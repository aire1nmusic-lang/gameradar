# Отмена Поддержки и возврат GS Coins

## Граница операции

`POST /api/v1/admin/support/:id/refund` отменяет одну ошибочную Поддержку и возвращает потраченные Coins **исходному игроку**. Это не возврат рублей, не вывод и не перевод Coins. Только подтвержденный аккаунт с назначенной ролью ADMIN и разрешением `support.refund`; собственную Поддержку администратор не отменяет. Причина — 10–1000 символов, `Idempotency-Key` — 16–128.

Исходные `gs_support` и отрицательная запись `SUPPORT` сохраняются. Одна PostgreSQL-транзакция создает положительную запись `REFUND`, неизменяемую `gs_support_refunds`, audit, новую версию сервера и публичный snapshot в outbox. Повтор того же запроса возвращает прежний результат; другой payload с тем же ключом или вторая отмена — 409. Сбой любого шага откатывает баланс, возврат и очередь вместе. Повтор первоначальной Поддержки не восстанавливает отмененную операцию.

Публичные суммы, участники и последние поддержавшие читаются через `gs_active_support`. Народный рейтинг остается независимым. D1 получает только новые суммы и количество участников через существующую подписанную доставку; причина, пользователь и ledger туда не передаются. На админской странице сохраняется история с причиной и временем отмены. Обновление D1 может задержаться; источник истины — PostgreSQL.

## Развертывание и откат

1. Сначала сохранить и проверить backup существующей базы, зафиксировать commit приложения и сохранить образ предыдущего API.
2. Выполнить read-only `node private-api/migrate-cli.mjs --plan` в целевом окружении. После версии 20 ожидается только `021_support_refunds.sql`; сравнить fingerprint с локальным планом. Другой набор миграций — остановка.
3. Применить этот fingerprint через `--apply --expect-sha256=…` с `MIGRATION_BACKUP_REFERENCE`. Миграция добавляет таблицу, view и ADMIN-разрешение; не удаляет и не переписывает данные. Проверить сохранность исходного ledger, баланса, Support и outbox. Только затем запускать новое приложение: его публичные запросы зависят от view.
4. Проверить права GET/POST, список ADMIN и публичные агрегаты. Живую финансовую корректировку выполнять только на согласованной тестовой операции; не начислять произвольные production Coins для проверки.
5. До первого возврата можно вернуть прежнее приложение, оставив добавленную схему. **После возврата старое приложение небезопасно:** оно снова считает отмененную Поддержку активной. Откат после использования — выключить операции отмены в UI/API, оставить новое чтение агрегатов и сохраненные ledger/refund/outbox. При необходимости backport чтения `gs_active_support` в предыдущий образ. Не удалять возврат или ledger и не понижать публичную версию. Исправление ошибочной отмены требует отдельной проверенной компенсирующей операции; автоматического restore пока нет.

## Проверки

`npm run test:private`: ADMIN и прямое разрешение без роли; запрет self-review/foreign Origin; возврат только исходному аккаунту; все три игры; уникальные участники и пустые агрегаты; повторы/конфликты; одновременные решения двух ADMIN; сохранение исходного ledger; неизменяемые возвраты; отказ outbox и полный rollback; приватность snapshot; Народный рейтинг неизменен; сверка ledger/баланса.

`node --test tests/private-migration-plan.test.mjs tests/yandex-private-gateway.test.mjs`: upgrade 20→21 с существующей Поддержкой и outbox, fingerprint, отсутствие неявной миграции, маршрутизация нового ADMIN endpoint. PGlite моделирует SQL/транзакции; это не доказательство конкурентности нескольких production PostgreSQL-соединений или живой приемки.

Robokassa остается test-only. Ее официальный [модуль WordPress](https://github.com/robokassa/cms-wordpress) указывает, что Refund API доступен для реальных платежей Robokassa Россия. [Тестовый режим](https://docs.robokassa.ru/ru/testing-mode) не переводит реальные деньги. Этим срезом внешние refund API и реальные продажи не включаются.
