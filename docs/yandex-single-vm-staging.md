In [Object Storage](https://yandex.cloud/ru/docs/storage/pricing), the *account-wide* first 1 GB of STANDARD storage and monthly request allowances are free, then roughly 2.376 ₽/GB-month for STANDARD storage. Existing buckets may already consume the allowance. The form's default **Cloud Backup** would instead add 280.80 ₽/month to attach the VM, plus **4.97 ₽/GB** of stored copies; its draft total was 1,791.36 ₽ **before public IP and backup storage**. At 1,700.29 ₽/30 days, 36 days of VM plus IP is about **2,040.35 ₽**; this is an arithmetic scenario, not an account-wide bill or proof of grant eligibility for each service. The remaining grant cannot be treated as a hard cap. [Yandex budgets only alert and do not stop consumption](https://yandex.cloud/ru/docs/billing/concepts/budget). Set low thresholds and an operational stop procedure before creation. Verify the grant scope, current consumption and exact total in the account again at the creation step.

## Prepared portable runtime

`deploy/vm/compose.yaml` puts PostgreSQL 17 and the Node private API on one Docker-only network; only Caddy exposes 80/443. PostgreSQL has TLS enabled with an explicit CA mounted into the API. `PRIVATE_RUNTIME=vm` removes the Yandex timer dependency. The VM runs `npm run private:maintenance-once` from host cron; `/__internal/maintenance` returns 404 in VM mode. Caddy overwrites `X-GS-Client-IP` with the direct socket peer and adds a 32+-character proxy secret; the backend returns `unknown` for an absent/invalid token or IP. No public client IP header is trusted. If the existing Yandex gateway sits in front of Caddy, the gateway may become the peer; **do not accept anti-fraud/rate-limit production behavior until staging verifies real client IPs through the full route**. Do not use `X-Forwarded-For` from the browser as a shortcut.

The image no longer bakes in a Yandex-only PostgreSQL CA. Supply `PG_CA_FILE` for either Yandex-managed or self-managed PostgreSQL; `postgresStore` verifies TLS and rejects URL TLS overrides. App settings remain environment variables. The [Caddy reverse proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) confirms `header_up` overwrites incoming headers. The direct socket peer, exact certificate chain and routing still require a live test.

## Deployment sequence after a reviewed spending approval

1. In the console, stage the same non-preemptible VM shape, with a cost alert and SSH/OS Login access. Restrict network rules to SSH from an operator address and HTTPS/HTTP only as needed. Keep PostgreSQL port 5432 and API port 8080 unpublished. Confirm grant expiry and full monthly quote before clicking **Create VM**. Do not attach the default Cloud Backup if using the encrypted database dumps below.
2. Install Docker Compose, Caddy only through the pinned image in the template, GnuPG and AWS CLI from their official sources. Copy `deploy/vm` to the VM; create `.env` from `.env.example` with `chmod 600`, real independent random secrets, and a staged API hostname. Do not commit `.env`, keys or private certificates. The existing production API gateway is unchanged until separate cutover review.
3. Run `sudo bash init-pg-tls.sh` in `deploy/vm` to create a self-signed PostgreSQL server certificate valid for Docker DNS `postgres` and mount its certificate as the API CA. The script refuses to overwrite an existing key, resolves the `postgres` UID from the image and checks the certificate. It expires after 90 days: schedule a reviewed rotation. Then test a verified TLS handshake; file permissions and connection still require a Docker rehearsal.
4. Run `docker compose config` and build on a disposable VM. Bring up PostgreSQL and the API, inspect health, then use `npm run db:private-plan` against the **empty staging database**. Apply only the reviewed fingerprint with a recorded backup reference using `db:private-apply`; the API never migrates implicitly. Seed only disposable test data. Run the full player/owner/admin HTTP journeys for L2, Minecraft and GTA RP and measure memory, CPU, response time and projection lag. If 2 GB / 20% CPU fails, stop and reprice before resizing.
5. Configure a private Object Storage bucket in the same Russian region, lifecycle retention, a write-limited service account, and a GPG public encryption key whose private restore key stays **off the VM**. `backup.sh` streams `pg_dump -Fc` through GPG, uploads it and verifies the object is nonempty. Schedule daily with `flock` and alert on failure. Test decryption and `pg_restore` into a **separate disposable database** before claiming backups work. This is database backup only: save the deployment config/secrets securely off-VM as well. Record measured backup size and storage cost. Set a retention policy before accumulating copies.
6. Cron example after validation: `* * * * * cd /srv/gamescout/deploy/vm && flock -n /run/lock/gamescout-maintenance.lock docker compose exec -T api node private-api/maintenance-once.mjs`. Observe failures and projection lag. Keep mail disabled until a verified Russian sender is configured. Keep real Robokassa sales disabled.

## Cutover and rollback gate

Before changing any production route: verify OAuth callback URLs, email, Telegram/OpenRouter data minimization, the real test merchant, Caddy/gateway client IP, D1 read-only mode, idempotent projection delivery and lag alarms on staging. Capture the old gateway spec and a tested PostgreSQL backup/restore point; freeze writes during any production data migration, reconcile counts and outbox versions, then switch only the private API route. Reverse the route if acceptance fails, but reconcile any new private writes before allowing the old D1 writer again. DNS, real payments and production migrations require separate approval with the tested rollback plan.

Migration to Amvera later is a **rehearsed** `pg_dump`/`pg_restore` of PostgreSQL plus the same container/env, not a guaranteed 10–30-minute window. Time and downtime depend on measured database size, upload bandwidth, restored indexes and verification. Amvera changes the original Yandex private-data location; its contractual/data-region and TLS/backup checks remain open. The original [hosting comparison](yandex-private-hosting-options.md) still records other options.
