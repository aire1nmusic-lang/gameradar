# Telegram: безопасное подключение администратора

## Граница

Бот отправляет администратору фиксированный тип события и случайный ID из private outbox. Сохраненный свободный текст уведомления не отправляется. Email, IP, материалы претензии, платежи, пользовательские сообщения и секреты не входят в payload. Команды управления production, callbacks и AI auto-fix не включены.

Доставка выполняется существующим maintenance на Yandex VM. Новые сервисы и платные ресурсы не нужны. Telegram получает chat ID администратора и bot token как служебные данные подключения; они не относятся к публичной проекции и не должны попадать в GitHub/Cloudflare.

## Подключение

1. Владелец создает бота через BotFather; токен сохраняется только в ignored `output/telegram-bot-token.txt`.
2. Владелец отправляет `/start` именно созданному боту в личном чате.
3. Проверить `getMe`, отсутствие неожиданного webhook и наличие ровно одного подходящего private `/start`. Не выводить raw updates, chat ID, имя пользователя или token. Пустая очередь не означает подтвержденного получателя.
4. Передать только `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_CHAT_ID` через защищенный SSH stdin в `.env` существующей VM. Не менять остальные переменные. При конфликтующих существующих настройках остановиться. Режим файла `0600`.
5. Пересоздать только compose service `api`, проверить health и наличие настроек без вывода значений. База, DNS, gateway и регистрация не меняются.
6. Проверить доставку настоящего ожидающего события через `dispatchTelegram`: успешный ответ Bot API и `delivered_at`. Не выдавать конфигурацию или локальный тест за доставку. Не отправлять ложный incident/recovery ради проверки.

В текущей сессии подготовлен локальный ignored helper `output/connect-telegram-vm.mjs`. Он не выполняет SSH до получения одного private `/start`; при ошибке настройки/health удаляет только добавленные им Telegram-ключи и возвращает API без них. Скрипт не является репозиторным артефактом или постоянным способом управления секретами.

## Откат и эксплуатация

Отключение: убрать только две Telegram-переменные из VM `.env` и пересоздать API. Outbox сохраняется для последующей доставки. Не удалять финансовые/claim/copyright записи. При компрометации токена владелец отзывает его через BotFather и предоставляет новый.

Повторные попытки ограничены тремя на событие. Не сбрасывать attempts массово: сначала выяснить причину. Ошибки доставки видны в operational snapshot; сообщения не содержат raw ошибок провайдера. Один cron на VM не обнаруживает смерть всей VM — независимая проверка uptime остается отдельным незакрытым пунктом.

Фактическое состояние 01.10.2026: получатель подтвержден и VM env подключен, но sendMessage не доставлен (projection.lag attempts=3). getMe внутри API-контейнера — TimeoutError, с ПК — успешен. Security group разрешает EGRESS ANY/all IPv4; это исключает только явный запрет в проверенных правилах, не все причины сети. Не включать платный AI, proxy/VPN или новый monitoring-сервис ради обхода невыясненного сбоя. Следующая диагностика: DNS/NAT/host-vs-container, с фиксированными кодами ошибок без секретных URL. После устранения причины повторить только конкретное остановленное событие и проверить delivered_at.
