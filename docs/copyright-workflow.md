# Copyright workflow — local core slice

`/copyright` accepts a claim about one existing external link slot (`site`, `discord` or `telegram`) on a registered L2, Minecraft or GTA RP server. The form requires claimant/contact, rights basis, work description, evidence, exact URL and server ID. The private API checks the current public catalogue URL before allowing automated analysis. Missing detail or a mismatched link becomes `NEEDS_INFO`, queues a clarification email and does not restrict anything. The submitted evidence and contact remain in private PostgreSQL; only server ID, slot name, projection version and claimed flag may enter D1.

A complete claim enters `PENDING_AI`. When an explicit OpenRouter key and copyright model are configured, the leased worker returns `VALID`, `DOUBTFUL`, `FAKE` or `INCOMPLETE`. Valid/doubtful classifications create a temporary restriction for that claim and exact slot and write a public projection event in the same PostgreSQL transaction. A clear fake does not restrict. Incomplete analysis asks for detail. AI output is triage, never a final legal decision. If the model is missing or fails, the link stays visible and the case remains in the manual queue; provider errors retry with backoff. An authorized copyright reviewer can restrict, restore, reject or request information with a written reason. Separate active claims on the same slot must each be restored before the slot reappears.

The public Worker reads `restricted_links` from the monotonic D1 projection and removes those URLs from its DTO. The private-mode server page also queries current private restrictions and hides all outbound links until that query completes, failing closed if it fails. This interim gate covers local/private-mode presentation while the D1 event is delayed. Before production cutover, require a projection lag alert and verify the live Worker has applied D1 migrations 0007/0008. Never publish legal text, contact data or evidence to D1. A server card remains published when a link is restricted.

Telegram notifications are queued transactionally, include only event, claim ID, server ID, scope and AI classification, and retry with a lease. `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ADMIN_CHAT_ID` are required for delivery. System queue counts and oldest pending Telegram event appear in `/admin/system`. OpenRouter requires `OPENROUTER_API_KEY` plus `OPENROUTER_COPYRIGHT_MODEL`; no default paid model is selected. A separate low-balance alert and management-key integration remain to be built. No external call was made in this slice.

Rollback: disable OpenRouter/Telegram workers, stop new copyright submissions, inspect pending private outboxes, and retain all claims/audit/restrictions. To undo a specific active restriction, use the authorized RESTORE action with a reason; it creates a new monotonic public snapshot. Wait for delivery and check the Worker HTTP response before considering the link restored. Migration 008 is additive and applied only locally. Back up PostgreSQL and D1 before any production migration; never drop the restriction column while a Worker version still reads it.

Official API references checked 27.09.2026: [OpenRouter chat completions](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request) and [Telegram Bot API sendMessage](https://core.telegram.org/bots/api#sendmessage). External credentials, email sender, production endpoints and legal/fiscal approvals remain separate blockers.
