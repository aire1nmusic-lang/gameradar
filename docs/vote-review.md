# Reversible vote review (local candidate)

Migration `020_vote_review.sql` keeps every accepted vote as private evidence and adds `ACCEPTED` / `VOIDED` review status. ADMIN and MODERATOR receive `votes.manage`. A reviewer must supply a 10–1000 character reason and cannot review their own vote. The status update and append-only audit event share one PostgreSQL transaction; a failed audit rolls back the decision. Repeated decisions are no-ops. The admin list shows the status and last reason.

The People's rating counts only `ACCEPTED` votes inside the configured rolling window. `VOIDED` votes still count against the account's repeat window and daily IP/device/ASN risk thresholds: excluding a suspicious vote does not let the same account farm replacements. A replay of the original idempotency key returns the same vote ID with `accepted:false` while voided. Restoring it returns that original vote to the rating only if it is still within the live window. No public D1 vote row, device hash, IP hash, reviewer identity or reason is projected. Money and Support do not enter the rating query.

**Verification:** PGlite test covers permissions, no deletion, rating change, repeat/idempotency guard, single audit on duplicate action, restore and transaction rollback if audit insertion fails. Full private suite 29/29, migration-plan tests 2/2 and typecheck passed. After restarting the local API and applying migration 020, the in-app browser showed three fixture votes and enabled reviewer controls on `/admin` at 390 px. The first mobile pass exposed horizontal overflow from long vote/user IDs; `break-words` removed it (`scrollWidth` 385 vs viewport 390). A live browser click changing a vote was not performed; the mutating path was exercised by the PGlite HTTP test. Migration 020 has not run in Yandex.

**Rollback:** use `RESTORE` with a recorded reason for an erroneous void; keep both audit events and the vote. If the application must be rolled back before migration 020 reaches production, stop reviewers first; the additive columns may remain. Never erase a vote or audit row to force a rating. A later production migration needs the separate backup/fingerprint gate.
