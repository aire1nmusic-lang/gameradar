# Private/public API route split candidate

`ru-proxy/yandex/gateway.private.template.yaml` is an **unapplied** candidate for the existing Yandex API Gateway. Generate it from the current static-prerender candidate with `node scripts/yandex-private-gateway.mjs --write`; `--check` detects drift. It retains the Object Storage site routes. The paths under `/api/v1` separate the two data owners on one HTTPS host:

| Destination | Routes |
| --- | --- |
| D1 relay, GET only | games, servers list/detail/online history, existing public rating, public Support aggregate, API sitemap |
| Private Yandex container | health, auth, email changes, Claims, owner review, scoped manage access, People's rating/votes, Coins, payments, Support transactions/detail, admin, copyright |
| Fixed 404 | any other `/api/*` route, including legacy D1 votes, Claim, account or event writes |

The public `GET /api/v1/support/ranking` uses D1's projected aggregate; the private API has an equivalent local implementation for development but the gateway deliberately selects the exact public route. The old `/api/v1/rating` is a **public catalog ranking**, not the new People's rating; the new UI uses `/api/v1/people-rating` for organic vote order. Existing `/dashboard` operations such as vote integration/API keys, and the old `/add-server` write, will receive 404 under this candidate until rebuilt against private Claim/review flows. They must be hidden or migrated before launch. `/__internal/maintenance` is absent from the gateway and must remain IAM-only on the container.

The relay Worker must also have `PUBLIC_ONLY=true` **at cutover**, not just the gateway path split: its origin address and other legacy routes may otherwise still write private D1 rows. The signed `/api/internal/public-projection` endpoint remains available to the private outbox even in `PUBLIC_ONLY` mode. Public-only D1 migrations, private PostgreSQL migrations, public dataset/ID mapping, projection signing secret and authoritative writes need verification before flipping this flag. Do not deploy the flag earlier while the legacy production flows still serve users.

The container integration requires a gateway service account with `serverless-containers.containerInvoker` on that container. The relay retains its existing function and service account. Replace placeholders only in a review copy outside Git, preserve the current gateway spec for rollback, and validate the route precedence and HTTP behavior on an isolated staging gateway with a staging container/DB and read-only public catalog. Test at least one request per row above, a legacy write denial, a forged `/__internal/maintenance` request, `Set-Cookie`, OAuth callback, client IP, and a missing static route. Then rehearse restoring the previous gateway spec and disabling new writes/timer. Do not route real users, apply production migrations, or change DNS until separately approved.

Local evidence: `node --test tests/yandex-private-gateway.test.mjs` checks every private API declaration against the route manifest, explicit public reads, legacy-write denials, generated spec drift, and the internal path exclusion. This checks source shape and documented [Yandex route priority](https://yandex.cloud/en/docs/api-gateway/concepts/) only; the gateway parser and live HTTP are **BLOCKED** because the Yandex CLI/authenticated staging container are unavailable here. [Container integration](https://yandex.cloud/en/docs/api-gateway/concepts/extensions/containers) and [dummy 404](https://yandex.cloud/en/docs/api-gateway/concepts/extensions/dummy) follow official extension fields. This local candidate creates no resource and costs 0 ₽. A staging container/DB can incur usage charges and needs a configuration-specific cost cap before creation.
