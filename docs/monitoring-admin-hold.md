# Admin hold for an owner monitoring target

Migration `019_monitoring_holds.sql` adds a private hold per server. A reviewer with `servers.review` may suspend an enabled owner target or restore it with a reason. The reviewer cannot act on their own server. Each transition locks the private server row, updates the hold, increments its version, queues a public snapshot and appends an audit entry in one PostgreSQL transaction. Repeating the same decision changes nothing. A failed outbox insert rolls the hold and version back.

While held, the owner sees the hold in `/account` and cannot re-enable or replace the target. They may disable their own saved target. The public snapshot contains only `monitoring: {enabled:false}`, so D1 stops probing and hides any stale player count. The private reason, reviewer, owner and target credentials do not enter the public snapshot. A reviewer restore removes the hold; it re-enables the owner's saved target only if the owner has not disabled it. No player count is inferred from restoring a target; a later successful probe must provide it.

For staging, apply the reviewed PostgreSQL migration after a verified backup, deploy the private API and UI, exercise suspend/restore on a labelled fixture, confirm monotonic D1 versions and `UNKNOWN` online, then inspect audit and projection lag. Migration 019 is additive and has not run in Yandex Cloud. Rollback is a later audited `RESTORE` action, or an owner disable followed by restore if the target must remain off. Preserve prior audit, outbox events and online samples. Do not decrement the public version or erase a private record to imitate rollback.
