# Private API container candidate — no cloud resource created

The private API must own users, sessions, Claims, votes, antifraud, Coins, payments, copyright, audit and outboxes in Yandex PostgreSQL. Cloudflare/D1 remains the public catalog and projection. The candidate `private-api/Dockerfile` packages the Node 24 HTTP service and Yandex's published PostgreSQL CA, without application secrets. Production listens on Yandex's `PORT` at `0.0.0.0`; local development stays on `127.0.0.1`. Production does **not** run background `setInterval`, because an idle Serverless Container cannot be relied on to execute it. A Yandex timer should invoke `POST /__internal/maintenance` every minute using a service account, its configured trigger ID/folder ID, and a random payload whose SHA-256 hash is supplied separately to the container. The container must stay private to IAM; the public API Gateway must not route `/__internal/*`. The handler processes bounded batches of mail, public projection, nickname/copyright AI and Telegram outboxes, checks projection lag and schedules the OpenRouter balance check in PostgreSQL. Outboxes retain their existing lease/retry/idempotency behavior.

[Yandex container HTTP mode](https://yandex.cloud/ru/docs/serverless-containers/concepts/container) requires the service to listen on `PORT`. [Timer triggers](https://yandex.cloud/ru/docs/serverless-containers/concepts/trigger/timer) invoke containers with event JSON; the [trigger API](https://yandex.cloud/en/docs/serverless-containers/triggers/api-ref/Trigger/create) supports a target path. [Invocation docs](https://yandex.cloud/en/docs/serverless-containers/concepts/invoke) say Yandex appends the caller IP to `X-Forwarded-For`, so the API uses the **last validated address** and ignores caller-supplied earlier entries. A missing/invalid address becomes unknown; ASN is not yet supplied by a trusted source. The [managed PostgreSQL connection guide](https://yandex.cloud/ru/docs/managed-postgresql/operations/connect/) provides the CA URL used in the image. TLS certificate validation remains enabled.

Required release inputs: chosen PostgreSQL cluster/FQDN, database credentials via Lockbox or equivalent, `DATABASE_URL`, `PUBLIC_ORIGIN`, `PUBLIC_CATALOG_ORIGIN`, `PUBLIC_PROJECTION_URL` and secret, `MAIL_ENCRYPTION_KEY`, `RATE_HASH_KEY`, Yandex folder and timer IDs, timer payload/hash, service-account permissions, verified mail sender, OAuth app IDs/secrets and registered callbacks, Turnstile keys, and optional Robokassa test/OpenRouter/Telegram settings. Never put any of these values in Git or the browser. The Yandex environment-variable total-size limit must be checked, especially if supplying a CA PEM through an env var instead of the included file. The timer path must be excluded from all public gateway specifications, and the container must not be made publicly invokable.

**Before creation:** obtain an approved region, host class, disk, backup and monthly cap. The prior single-host PostgreSQL example is about 6,001.92 ₽/month for 720 h with 100 GB network HDD; HA, extra backup and traffic add cost. The [Serverless Containers price schedule](https://yandex.cloud/ru/docs/serverless-containers/pricing) is usage-based. At 1 GB RAM, 0.5 vCPU, a one-minute timer averaging 2 seconds per call would consume about 24 GB·h RAM and 12 vCPU·h in 30 days; after the included 10 GB·h and 5 vCPU·h, that is roughly **92.89 ₽/month** for the timer before API traffic, registry, gateway, egress and provisioned-instance costs. This is an illustration, not a selected configuration or spending approval. New cloud spend so far: **0 ₽**.

**Release order after approval:** create/secure PostgreSQL and verify a backup/restore; export legacy D1 private rows and reconcile counts; apply numbered private migrations 001–014 explicitly with a rollback/restore plan (production startup never migrates); import public server registry and bootstrap one ADMIN; build and test the image, create a private container revision and timer, verify event authentication and outbox lag; validate the [gateway route split](yandex-private-gateway.md) on staging, including the relay Worker's `PUBLIC_ONLY=true` boundary at cutover; verify email/OAuth/test payment/AI/Telegram on staging; rehearse rollback; then consider production routing and DNS separately. The current gateway still routes `/api/*` to the legacy D1 relay, so container readiness does **not** mean the private API is deployed or reachable to players.

**Rollback:** stop new private writes and timer, restore the previous gateway spec and static site, then restore PostgreSQL from the verified backup if a migration cannot be rolled forward. Reconcile any already delivered public versions; do not delete ledger/audit records or rewrite a D1 projection backward. No Docker image was built on this machine because the Docker daemon is unavailable; no Yandex container, timer or database was created.
